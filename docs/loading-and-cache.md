# 分片加载与本地缓存

整库一万五千个图标、几十 MB 的图形 —— 怎么让首页只花 27 KB、刷新不发一个请求。
这一篇记做法、数据,以及踩过的坑。

## 一、问题

一开始整库是**一张 sprite + 一份清单**:

| | 原始 | 压后 |
| --- | ---: | ---: |
| `sprite.svg`(全部符号) | 5.5 MB | 1.27 MB |
| `manifest.json`(全部条目) | 9.5 MB | 383 KB |

页面为了显示几十个图标,得把这两个整包拉下来 —— 首屏白等几秒。
而库里九成是 emoji(8990 个,三个集各有各的画法),却挤在同一张 sprite 里。

## 二、做法

### 1. 分片

每个分类按清单里的 id 顺序切,一片 = 一个 sprite 文件,**≤80 个符号**
(首页只摆 60 个,一片正好装得下)。
片的**大小按压后算:每片不超过 1 MB**(边缘自动 brotli)。
切的时候先按原始体积粗切,压一压看超没超,超了对半再切。

现在 **222 片**,最大的一片 106 KB 压后。

### 2. 默认只下 star 那一小片

`star.tsv` 里每类挑 2 个,84 个符号 —— 首页就下这一片:

| | 原始 | 压后 |
| --- | ---: | ---: |
| `index.json` | 19 KB | 4 KB |
| `manifest.star.json` | 34 KB | 6 KB |
| `sprite.star.svg` | 82 KB | 17 KB |
| **首页合计** | 135 KB | **27 KB** |

默认只摆 60 个。

### 3. 搜索才下全名单

用户一搜索,下 `manifest.json`(全名单)本地过滤;点分类 chip 就只下那个分类的清单。

清单里只放**英文(原版)+ 结构信息**,中文名单独一份 `manifest.zh.json`,
切到中文时才下 —— 英文区根本不碰它。
能从 id 或分类推出来的字段(路径、sprite 符号 id、出处、许可、单色标记)一律不带:
清单是搜索时一次下下来的,每一字节都要省。

### 4. 显示按需取片,取回后注入页面

片取回来之后,把里面的 `<symbol>` **注入页面**上一个隐藏的 `<svg>`,
图标用 `<use href="#符号id">` 引用本地符号 —— 一片只解析一次。

> 之前试过 blob URL:每个 `<use>` 引用一次 blob 会被反复解析,
> 网络面板里还会刷出几十条 blob 记录(其实一个网络请求都没有)。注入页面就没这问题。

### 5. 本地缓存

下过的资产留在浏览器本地,下次直接用 —— 用的是 **Cache API**。

## 三、缓存的三层

```
Cache API 命中 → 直接用(零请求)
  ↓ 没命中
HTTP 缓存命中 → 浏览器直接给(也不出网)
  ↓ 还没有
网络 → 下下来,同时存进 Cache API
```

实测:刷新时(缓存热着)只有页面本身走网络,那些资产**根本没发请求**。

把 Cache API 清掉再刷新,就能看到中间那层:

```
/icon/                     ← 网络(页面本身)
/icon/sprite.star.svg      ← HTTP缓存(磁盘)
/icon/index.json           ← 网络
/icon/manifest.zh.json     ← 网络
/icon/manifest.star.json   ← 网络
```

那三条清单每次都问服务器,是因为它们原来发的是 `max-age=0, must-revalidate`。
现在改成一天了(URL 上带 `?v=构建号`,内容变了 URL 就变)。

## 四、浏览器的存储:能用的那几个

| | HTTP 缓存 | Cache API | IndexedDB | OPFS |
| --- | --- | --- | --- | --- |
| 模型 | 网络响应的缓存 | `Request → Response` 键值对 | 对象仓库(键值 + 索引) | **真的文件系统**(目录 + 文件) |
| 键 | URL | URL(自定义 Request) | 任意 | 路径 |
| 读 | 隐式 —— fetch 时浏览器自己判断 | `await cache.match(url)` | 事务 + objectStore | `getFileHandle()` → File |
| 写 | 自动(受 Cache-Control 管) | `cache.put()` | 事务 | `createWritable()` **流式** |
| 随机访问 | 不行 | 不行(整个 body 读进内存) | 不行 | 行(worker 里 `createSyncAccessHandle()`) |
| 大文件 | 会进内存 | 会进内存 | 会进内存 | **按块读写,不占内存** |
| 结构 | 平的 | 平的(URL 列表) | 仓库 + 索引 | **目录树** |
| 语义 | 带 header/status | 带 HTTP 语义 | 无 | 无(就是文件) |
| 配额 | 磁盘的一个百分比 | 同左,四个共享 | 同左,共享 | 同左,共享 |
| 淘汰 | 浏览器 LRU | 浏览器 LRU | 浏览器 LRU | 浏览器 LRU |
| 适合 | 静态资源(改了 URL 就换一份) | 静态资源的**显式**缓存 | 结构化数据、离线库 | 大文件、随机访问 |

顺带记一个**死了的**:**WebSQL**(把 SQLite 直接暴露给网页,真 SQL)。
2009-04 提议,2010-11 W3C 工作组**放弃**(没达成共识)→ 从未成为标准;
Firefox 从没实现过;Safari 2019 弃用;Chrome 119(2023)移除。
死因不只是技术:当年提它是因为**还没有 IndexedDB**;等 IndexedDB 落地(2015),
它的理由就没了,连 Google/WebKit 自己也不再推。

### 为什么我们用 Cache API

**不选 localStorage**:它存字符串、只有 5 MB,全名单一个文件就 3.1 MB,片根本存不下。

**不选 IndexedDB**:我们要存的就是「文件 → 一段文本」,正好是键值对,Cache API 的形状天生对;
IndexedDB 得自己写事务、自己设计 objectStore,存进去还得再取出来转字符串 —— 那套我们用不上。
IndexedDB 真正该用的场合:结构化数据(离线草稿、按字段查的记录)。

**不选 OPFS**:它是文件系统(目录 + 文件、流式写、随机访问)——
这些长处对"只读的资源缓存"一条都不成立:我们的片都是几百 KB 的一次性文本,
不需要流式写、不需要随机访问、不需要目录树。要挑一个更"现代"的组合
(OPFS 存图形 + Cache API 存清单),那是给十万级、GB 级的场景准备的。

**没有 Cache API 的环境**(老 Safari、`http://` 的局域网地址)要降级:
之前 `caches` 未定义会抛 `ReferenceError`,整个启动流程挂掉 → 页面空白。
现在降级成不缓存:每次现下,只是慢一点,页面照常用。

**Cache API 自己不压缩** —— 存的是你给它的正文。我们给的是解压后的文本
(全部片 50.1 MB),自己用 `CompressionStream` 压一遍再存:6.5 MB,省七倍多。
压缩在后台做,不挡渲染。

## 五、实测

### 线上(po6.sh/icon)

| 场景 | 请求 | 耗时 |
| --- | --- | ---: |
| 第一次来 | 5 个(共 27 KB) | 0.72 s |
| **刷新** | **1 个(只剩页面本身)** | **0.38 s** |
| 点一个分类 | 首次 1 个,之后 **0 个** | 0.11 s |
| 搜索 | 全名单 + 用到的那几片 | — |

### 点一个分类要多久

点分类 chip 曾经是全站最卡的地方:渲染前要等所有片下完,界面冻着,
emoji 的片又大(1.5 MB)。四处一起改:

| 改法 | 效果 |
| --- | --- |
| 渲染不再等片 | 先画格子,片到了图标自己补上(SVG 引用是活的) |
| 片切小(300 → 80 个符号) | emoji 的片 1.5 MB → 106 KB |
| 清单和第一片并行拉 | 少一个来回 |
| 悬停 chip 就预取 | 点下去时东西已经在了 |
| 同一个资产只发一次请求 | 预取还在飞就点下去,不再重复拉 |

实测(线上,点最重的 Emoji(Noto)):

| 场景 | 之前 | 现在 |
| --- | ---: | ---: |
| 悬停一下再点 | 1419 ms | **37 ms** |
| 直接点(没预取) | 1419 ms | **379 ms** |

顺带:点开一个图标的「相关图标」原来要遍历全库 15187 个图标重算 tokens(17–31 ms,
直接掉帧),改成建索引后只查表(0.1 ms);「SVG 源码」那块原来要发请求去取图标文件,
现在直接从页面里已注入的符号取 —— 点图标零请求。

### 资源是"直取"的,Worker 只管页面

分片、清单这些静态资源**不经过 Worker** —— Cloudflare 的静态资源是直接由边缘发的
(实测:在 Worker 的资源分支上加个标记头,资源请求里根本没有那个头 → Worker 没跑)。

只有**页面 HTML** 是 Worker 现场生成的(它是同一个 Worker 挂的,得拼构建号、
处理两个挂载点前缀)。

```
/icon/                     ← Worker 现场生成(拼构建号、处理挂载前缀)
/icon/manifest.json       ← 边缘直发(静态资源,Worker 不参与)
/icon/sprite.star.svg     ← 边缘直发
/icon/i/**                 ← 边缘直发
```

想更彻底的话,可以把资源挪到另一个路径、让 Worker 完全不挡 —— 但现在这样
已经是最短路径了:资源请求一次到边缘,不用绕 Worker。

### 缓存用量

| 用到哪 | 缓存里几个 | 占多少 |
| --- | ---: | ---: |
| 看完首页 | 4 | 0.17 MB |
| 再搜索(下全名单) | 11 | 1.02 MB |
| 再点两个 emoji 分类 | 13 | 1.11 MB |

全部片都缓存住的话:6.5 MB(压缩后)。配额是磁盘的一个百分比 —— 这台机器 10 GB,
用掉 0.06%。

### 发出去的资产

| 资产 | 是什么 | 文件数 | 原始 | 压后 | 什么时候下 |
| --- | --- | ---: | ---: | ---: | --- |
| `index.json` | 索引:分类清单 + 每片多大 | 1 | 22 KB | **4 KB** | 第一个请求 |
| `manifest.star.json` | 精选那部分的清单 | 1 | 34 KB | **6 KB** | 首页 |
| `sprite.star.svg` | 精选那一片的符号 | 1 | 82 KB | **17 KB** | 首页 |
| `manifest.json` | 全名单(英文原版) | 1 | 3.0 MB | **160 KB** | 用户一搜索 |
| `manifest.zh.json` | 中文翻译包 | 1 | 766 KB | **86 KB** | 切到中文 |
| `manifest.<cat>.json` | 各分类的清单 | 47 | 3.0 MB | 183 KB | 点那个分类 |
| `sprite.<cat>.<k>.svg` | **片**(≤80 符号,压后 ≤1 MB) | 221 | 50.1 MB | 5.9 MB | 结果用到哪片 |
| `i/<cat>/**/*.svg` | 图标原文件 | 15,187 | 50.0 MB | 15.8 MB | 下载单个 / 看源码 |
| **合计** | | **15,460** | **107 MB** | **22 MB** | |

图标原文件不进我们的缓存:它们只在"下载"和"看源码"时按单个文件取,
走浏览器自己的 HTTP 缓存。

## 六、踩过的坑

1. **一个图标 = 一条清单项**。别名(`infra:server`)和具体版本(`infra/v0:server`)
   是同一个图标,不能各占一条 —— 否则搜索结果里同一个图出现两次。
   现在别名只是挂在推荐版上的另一个键。
2. **片要在渲染前就绪**,否则浏览器自己去拉,本地缓存就白做了。
3. **清清单要在分片之后写** —— 每个图标要标自己住哪一片,顺序反了清单里就没有 `shard`。
4. **Noto 的 SVG 原本不是合法 XML**:里面有一堆 `<i:aipgf>`(Illustrator 的元数据),
   前缀 `i:` 没声明;还有 `xmlns:x="&ns_extend;"` 这种实体型声明,
   而定义它们的 DOCTYPE 已经被去掉了。进 sprite 前要清干净。
5. **内部 id 要加前缀**:Noto 的渐变全都叫 `radial-gradient`,
   几百个合进一片必撞(跟 AWS 那批当年的问题一样)。
6. **缓存桶的名字要等构建号**:桶名 `icon-assets-<构建号>` 是在脚本加载时算的常量,
   而构建号是 Worker 注入的 —— 桶名会永远是 `icon-assets-dev`,发新版后旧桶清不掉。
7. **emoji 三个集各画各的**,键名对得上(`twemoji:grinning-face` /
   `fluent:grinning-face` / `noto:grinning-face`),
   打开一个的面板,「相关图标」第一条就是另外两版。

## 七、撑到十万个 emoji

同一套算法,只改三个数:

- **片数**:十万 / 300 ≈ 350 片 —— 片的大小不变,请求数不变(只下看得见的那几片)
- **全名单**:十万条 ≈ 60 MB 原始 / **2.4 MB 压后** —— 搜索时下一次,
  之后本地缓存顶着(Cache API 装得下)
- **缓存**:磁盘够,浏览器自己按最久没用的清

**算法不变,只把常数换掉。**
